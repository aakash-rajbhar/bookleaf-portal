# Decisions log (append: date, decision, why)

- D1: Express 5 + TypeScript. Async handler errors propagate automatically; simple, widely known.
- D2: `pg` + plain SQL migrations (no ORM). Schema design is graded; explicit SQL is easy to explain and agent-friendly.
- D3: SSE over WebSockets. One-way server->client is all we need; works over plain HTTP; auto-reconnect built in.
- D4: SSE auth via short-lived stream tokens: browsers' EventSource cannot send Authorization headers. Instead of exposing long-lived login tokens in URLs, clients exchange their Bearer token at POST /events/token for a 60-second single-purpose JWT ({purpose: 'sse'}). GET /events verifies purpose === 'sse' and rejects regular login tokens, while normal authenticate rejects stream tokens.
- D5: Gemini free tier behind LLMProvider interface + MockProvider so quota never blocks dev or the live demo.
- D6: AI triage runs async after ticket insert, so ticket creation never depends on the AI.
- D7: Plain SQL migrations executed within transactions and tracked via `schema_migrations` table for atomic, idempotent execution without heavy third-party migration tools.
- D8: Pinned JWT algorithm to HS256 on sign and verify, with dummy bcrypt comparison for unknown emails to prevent username enumeration timing attacks.
- D9: Book endpoints return 404 instead of 403 when an author requests a book owned by another author to prevent resource existence enumeration.
- D10: Author-facing ticket responses strictly omit internal and AI triage metadata (category, priority, AI fields, internal notes) and return 404 for tickets belonging to other authors.
- D11: SLA thresholds defined by priority (Critical: 24h, High: 48h, Medium: 96h, Low: 168h; null priority defaults to Medium). A ticket is flagged as isOverdue when unresolved ('Open' or 'In Progress') and its age exceeds its SLA limit.
- D12: Model = gemini-3.5-flash-lite (free tier). Measured with a one-word ping: 2.6s and 3.5s, 0 thinking tokens.
  gemini-3.5-flash rejected: 15-27s latency and thinking tokens consumed the output budget, returning empty text.
  gemini-3.1-flash-lite kept as an alternative (one 19.9s outlier in two runs). Triage and short drafts do not need
  deep reasoning, so a lite model is the right cost/latency trade-off. Free tier may use prompts to improve Google's
  models, so only the synthetic sample data is ever sent.
- D13: Rate limiter fails fast with sliding-window per-minute (AI_RPM_LIMIT) and per-day (AI_DAILY_LIMIT) caps. If a slot frees within 10s, it waits; otherwise throws AIUnavailableError('rate_limited') immediately rather than maintaining an unbounded queue, triggering graceful fallback and preserving responsiveness.
- D14: Total deadline (AI_TOTAL_TIMEOUT_MS, default 30s) bounds logical AI requests across retries and fallback models. Per-attempt timeout is min(AI_TIMEOUT_MS, remaining), and retries/fallbacks are aborted if <5000ms remains. Rate limiting is enforced per upstream attempt inside invokeModel (counting waiting time against the deadline), no retries are performed on timeout (failing fast to fallback), finishReason other than STOP is rejected as invalid_output, and cooldown periods prevent hammering during 429s.
- D15: Triage design: one generateJSON call classifies category, priority, and reason (<200 chars). Code-level guardrails enforce business policy (ISBN & Metadata Issues forced to at least High priority). Atomic SQL updates preserve admin overrides: fields with *_source='admin' are never overwritten by AI or fallback results. In-memory queue with single concurrency prevents thundering herds, with startup recovery on boot to re-enqueue pending tickets older than 1 minute.
- D16: Draft response design: on-demand and cached in `ai_drafts` so unopened tickets cost zero AI quota. Knowledge base context is strictly sliced by ticket category (tone + category section + example query only) to prevent policy hallucination and keep prompt size under ~1,000 tokens. Key facts (overdue status, rollover eligibility, production stage) are deterministically computed in pure code (`computeBookFacts`) rather than inferred by the LLM. When AI is unavailable or produces empty output, deterministic per-category templates (`source: 'template'`) guarantee immediate, grounded replies.
- D17: Overdue royalty detection and payout deadline assumptions: calendar quarters are assumed to end on Mar 31, Jun 30, Sep 30, and Dec 31, with payouts due within 45 days. The maximum allowable latency from reference date (last payout or publication) is defined as 135 days (90-day quarter cycle + 45 days, `OVERDUE_DAYS_THRESHOLD = 135`). Books with pending royalties >= Rs 1,000 exceeding 135 days are flagged as `likelyOverdue = true`, requiring direct delay acknowledgement and a 48-hour resolution commitment. These are recorded as engineering assumptions, not BookLeaf policy.
- D18: Token storage in `localStorage` vs `httpOnly` cookies: Auth JWT is stored in `localStorage` (`bookleaf_auth_token`) to simplify client-side Bearer token transmission across the Vite dev proxy and decoupled deployment architectures (e.g. Vercel frontend + Render backend) without requiring complex cross-domain cookie configurations (`SameSite`, CORS credentials, domain matching). XSS trade-off: While accessible to client-side scripts, the application avoids `dangerouslySetInnerHTML`, uses zero third-party tracking scripts, renders all author/book strings safely through React JSX text bindings, and validates all API shapes. For a production banking/payments system, migrating to an `httpOnly`, `Secure`, `SameSite=Lax` cookie with refresh-token rotation would provide superior defense-in-depth against script injection.
- D19: Author books & query UX rules:
  1) In-production books completely hide the sales and royalty block to prevent confusing authors with zero/unsettled counters before distribution.
  2) When pending royalties are positive on a book that has never had a payout (`lastPayoutDate` is null), a clear explanatory notice is shown ("No payout yet. Royalties are calculated quarterly and paid within 45 days of quarter end") rather than presenting an overdue state.
  3) Query submission form allows selecting in-production titles (as authors often ask about them) and supports "General / Account Level" queries by omitting `bookId`.
  4) Client-side validation mirrors backend Zod rules with live character counters, while preserving input state and field-level error mapping from server validation responses.
- D20: Real-time ticket updates via Server-Sent Events (`useTicketStream`):
  1) Token refresh on reconnect: Because browser `EventSource` cannot send custom headers and short-lived stream tokens expire in 60s (D4), automatic browser reconnection would reuse the expired token and fail with 401. `useTicketStream` explicitly traps connection errors, closes the stale `EventSource` instance immediately, and fetches a brand new stream token from `POST /events/token` using exponential backoff (1s, 2s, 4s... max 30s + jitter).
  2) Robust fallback polling: While the stream is disconnected or reconnecting (`status !== 'live'`), an interval polls the active page query every 30 seconds (`type: 'poll'`), ensuring the author never misses replies even if SSE is temporarily blocked or down. Polling immediately halts as soon as the stream becomes live.
  3) StrictMode & Lifecycle hygiene: Uses a cancelled flag and abort pattern to guarantee that React StrictMode double-mounting never opens duplicate streams. The callback reference is retained in a ref (`onEventRef`) so stream connections are not torn down on every component re-render.
  4) Seamless in-place updates: Real-time refetches update data without flashing full-page loading spinners, and monotonic request sequence IDs ignore out-of-order responses.
- D21: Admin ticket queue architecture and URL-synchronized state:
  1) URL-driven filter state: All queue filters (status, category, priority, assignment, date ranges, search query, and sort order) are synchronized bidirectionally with the URL query parameters (`useSearchParams`). This guarantees that browser refresh, back/forward navigation, and shared admin links restore the exact filtered view. Changing any filter automatically resets pagination offset to 0.
  2) Real-time live queue synchronization: Reuses `useTicketStream` on the admin stream (`admins` channel). Real-time events (`ticket.created`, `ticket.triaged`, `ticket.reply`) trigger an in-place background refetch of the active filtered page without unmounting or flashing loading spinners, preserving scroll position and table context. Monotonic request sequencing discards out-of-order asynchronous responses.
  3) Visual triage and urgency hierarchy: Backend urgency sort puts unresolved tickets first ranked by priority and age. Rows with SLA breaches (`isOverdue = true`) are prominent with a red left border and "Overdue" indicator, while resolved/closed rows are visually dimmed. AI states are clearly communicated (Classifying..., Rule-based fallback, or Admin edited).
- D22: Admin ticket detail and AI draft editor architecture:
  1) StrictMode-safe single-invocation draft generation: When opening an unreplied, non-closed ticket without an existing persisted draft, `POST /admin/tickets/:id/draft` is guarded by an invocation ref (`draftRequestedRef`) and keyed by ticket ID. This prevents React StrictMode in development from firing duplicate LLM draft requests and keeps backend AI token usage strictly at 1 per unread ticket. Re-opening a previously drafted ticket loads `latestDraft` from backend cache without making any LLM call or writing new `ai_usage_log` rows.
  2) Draft state isolation and non-destructive live updates: Admin reply text lives exclusively in the `DraftEditor` local state and is never overwritten or mutated by background SSE ticket refetches or stream events. Text is replaced only via explicit user actions ("Regenerate" with `window.confirm` protection if modified, or "Reset to draft"), or cleared upon a successful reply send.
  3) Grounded triage & Author book facts context: Author metadata and full book financial/operational facts (status, copies sold, MRP, royalty paid vs pending, last payout, distribution channels) are laid out in a dedicated context sidebar. In-production books display their workflow stage without false zero-royalty statistics, and books with accrued royalties and no historical payouts are highlighted as "Pending royalty, never paid".
  4) Strict staff-only boundaries: Staff internal notes have distinctive amber styling and explicit non-author labels; they are isolated in `InternalNotes` and never exposed or leaked to author clients or author ticket responses.
  5) Resilient manual degradation: When AI draft generation fails or is in fallback mode, `DraftEditor` displays the error banner and keeps the manual reply textarea fully usable and non-blocking, ensuring support agents can always respond promptly regardless of AI service availability.
- D23: Deployment topology, build isolation, and demo reset strategy:
  1) Decoupled compilation roots: Development runs TypeScript source and scripts directly via `tsx`, but production runtime requires compiled JavaScript in `dist/`. Compiling with a root of `.` in `tsconfig.json` generated nested `dist/src/` structures that broke `"main": "dist/server.js"`. Added `backend/tsconfig.build.json` strictly targeting `rootDir: "src"` and outputting directly to `dist/`, ensuring zero configuration drift between `npm run dev` and `npm run build && npm start`.
  2) Frontend SPA routing: Vercel static asset hosting returns 404 on deep links like `/tickets/:id` or `/admin/tickets/:id` on hard browser refresh without server-side rewrite rules. Added `frontend/vercel.json` routing all non-asset requests to `/index.html` to allow client-side React Router history navigation.
  3) Idempotent demo dataset: The 7 demo tickets span all key evaluation states (overdue SLA, in-production book, fallback rule-based classification, resolved query, closed ticket, pending royalty highlights). Tickets use fixed deterministic UUIDs and SQL `ON CONFLICT (id) DO NOTHING` with relative timestamps calculated at insertion time (`NOW() - interval '...'`), guaranteeing that re-running `seed:demo` never creates duplicate tickets or artificial data bloat.
  4) Destructive operation safety guard: Resetting demo state deletes all tickets, messages, internal notes, AI drafts, and AI usage telemetry without touching foundational author profiles, books, or user authentication records. To prevent accidental data wiping in production or shared environments, `reset:demo` enforces a strict guard requiring `CONFIRM_RESET=yes`.
